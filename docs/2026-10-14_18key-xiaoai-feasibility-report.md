# 小爱输入法 18 键键盘可行性评估

评估日期：2026-10-14。目标宿主：`com.xiaomi.type 0.2.1053.06f65b7c`，versionCode 21053。范围是本地源码、现有 APK、JADX/smali 产物和公开引擎文档。

## 结论

**技术上可以开发图片中的 18 键键盘，达到日常完整可用需要同时完成布局、歧义解码、选词和编辑状态适配。现有项目具备接入基础，但当前没有已验证可用的 18 键实现。**

布局层有明确的可改造入口，候选栏和文本提交也有可复用接口。最大的未知是讯飞底层能否接受“一次按键对应多个字母”；若不能，需要增加独立拼音引擎。已有形码原型只提供静态码表精确查询，并且尚未完成宿主真机验证，不能作为 18 键拼音已经可用的依据。本次没有实现或安装键盘；ADB 检测到未授权设备，没有进入设备执行测试。

建议先限定一个宿主版本，验证原生多字母输入接口；验证通过后继续复用讯飞，否则采用 Rime 解码并接入小爱现有候选和上屏管线。这里的“完整可用”指下文明确的功能和验收范围；原生云候选、原词频和整句效果是否能够沿用取决于引擎路线。

## 图片对应的布局和输入语义

图片的“18 键”只计字母键，Shift、删除、空格、标点和模式键另计。

| 行 | 字母键 | 数量 |
| --- | --- | --- |
| 第一行 | Q / WE / RT / Y / U / IO / P | 7 |
| 第二行 | A / SD / FG / H / JK / L | 6 |
| 第三行 | Z / XC / V / BN / M | 5 |

离线校验确认：18 个分组覆盖全部 26 个字母，字母没有遗漏或重复。假设中文点击多字母键表示该组任一字母，则：

- `nihao`（你好）对应 `BN → IO → H → A → IO`。
- `bihai`（碧海）也对应 `BN → IO → H → A → IO`。

所以一个完整实现必须允许这类歧义进入候选解码，并允许用户明确选择目标文字。英文、网址、邮箱、密码以及拼音修正需要确定字母的输入方式。图片还展示了数字、符号及全选、复制、粘贴、段首和段尾标记，但静态图片不能证明其触发手势。

建议产品语义为：中文点击进行分组输入；多字母键通过明确的弹出选择或滑动输入单个字母；英文模式也提供全部字母的确定输入。数字、符号及编辑快捷操作需要单独定义手势和提示。是否使用左右滑动、上滑或长按应在真机试用后确定，不能从截图宣称已经还原。

本报告主要评估 18 键拼音。虎码、五笔与 18 键共同使用需要另外定义分组重码及确定字母输入规则，不应因项目已有虎码就默认兼容。

## 原生 18 键支持：有探测入口，尚未证实

`com.iflytek.depend.common.pinyin.LayoutType` 只有中文九键、中文 26 键、英文九键、英文 26 键和笔画。宿主 `z8.g` 也没有 18 键引擎类型，键盘设置 XML 没有对应选项。

本次直接扫描原始 APK 的两份 DEX 字符串表：未匹配显式的 `18key/key18/18键/十八键` 名称；SDK 中保留了 `SMART_LAYOUT_13_KEY`。13 键常量不代表图片中的 18 键可启用，也不能据此认定 native 完全不支持自定义分组。

资源中的 `q18_outer/inner` 不能视为“18 键”证据：`ab.p1` 的相关分支由 `ma.o` 的折叠屏内外屏判断控制，仍调用普通 `ka.p` QWERTY 生成函数；`ma.d` 的枚举明确区分 `FOLDABLE_OUTER` 和 `FOLDABLE_INNER`。

两条值得限时验证的线索：

1. `ISmartEngine.inputKey(char[]) → DecoderManager.inputSpell(char[]) → c1 → m1 → XFInputDefaultCore.nativeProcessKeys(...)` 确实存在。本次校验了 native 方法声明。**数组可能有批量输入或其他语义，Java 签名不足以证明它表示一次按键的字母集合。** 此外 `c1.java:1269` 在非零 `realCursorPos` 分支使用单字符参数，需要特别验证组合态内移动光标后的编辑。
2. `LanguageModel` 有 `int[][] layoutParam` 和 getter/setter，但对当前 SDK Java 产物的检索只发现字段及访问方法，没有找到实际配置、读取和传入解码器的调用。这是待确认的字段，不是现成的自定义键位 API。

关键解码逻辑进入 ARM64 的 `libgeneralcore-jni-v1001.so`。本次读取 ZIP 内库文件并校验哈希，未做 native 函数反编译或运行测试。Java 层依赖为 `IPinYinEngine/DecoderManager`，JNI 边界是 `XFInputDefaultCore`；更多 ELF 依赖证据见[已有宿主分析](wubi-analysis-20261012.md)。

原生路线的首个验收门应是：点击 `WE` 只增加一位分组输入，后续字母能解出两条分支对应的拼音和词语；退格一次恰好删除这一位；选词、光标编辑和重建仍然一致。数组被解释为连续输入两个字母，或仅识别第一字母，都不能通过这一验收。

## 实现路线

| 路线 | 判断 | 可保留的能力 | 工作和限制 |
| --- | --- | --- | --- |
| 自定义布局 + 讯飞多字母输入 | 优先做限时探测，成功条件尚未证实 | 有机会继续使用原生词库、学习及云候选 | 需证明分组语义、模式参数和编辑行为，无法只凭常量启用 |
| 自定义布局 + Rime + 宿主接口桥接 | 技术依据较明确，作为原生路线失败后的开发方案 | 复用小爱界面、候选和提交；词库及规则自行配置 | 增加 ARM64 native/JNI 构建、库加载、方案部署、词库许可和用户数据持久化；候选效果由所选方案决定 |
| 自定义 Kotlin 拼音引擎 | 可以开发，但完整日常能力成本高 | 可以复用现有 Java/Kotlin 构建 | 需要自建音节切分、分组歧义、词典、整句排序、学习和混合输入，现有形码精确查表无法承担这些能力 |

Rime 的官方[拼写运算文档](https://github.com/rime/home/wiki/SpellingAlgebra)提供编码映射及拼写索引机制；[C API](https://github.com/rime/librime/blob/master/src/rime_api.h)提供会话、按键、组合态、候选、选词和提交接口。根据这些能力，可以设计把原拼音字母映射到 18 个代表码元的方案，再由引擎处理重码及词句解码。**这是有文档依据的设计推断，本次没有部署该方案，也没有验证在本宿主中的实际输入结果。**

例如以各组第一个字母作内部码元，完整字母表映射为 `abcdefghijklmnopqrstuvwxyz → abxswffhijjlmbipqrsruvwxyz`。`nihao` 和 `bihai` 都得到 `bihai`；这个内部编码应通过自定义方案解释，不能直接送入原生全拼引擎当作确定的拼音。

Rime 接入需要泛化现有桥接层。当前 `ShapeHostBridge` 直接依赖 `ShapeEngine`，选词会清空整个编码，且没有拼音的分段确认、连续组句和光标语义；不能直接把 Rime 候选列表塞入现有代理就视为完成。现有最大码长和满码自动上屏规则也不适用于长拼音。

独立引擎不自动拥有小爱的原生云候选和原用户词频。工具栏、剪贴板、语音和 AI 面板可以尝试沿用宿主，但进入和退出这些面板时必须同步组合状态；它们的兼容性仍需要真机验收。

## 必要改动

1. 增加独立 18 键模式和选择入口，保存用户选择；明确与原生 26 键、九键、双拼及形码的优先关系。宿主内部可以暂借 PINYIN/QWERTY 标识，但模块必须保存真实模式，避免英文或符号界面被误替换。
2. 新增布局构建器，按图片建立 18 个字母键及控制键，接入布局重建；适配键盘高度、横竖屏、屏幕宽度、深浅色和现有外观配置。
3. 新增按键与手势适配，区分分组输入、确定字母、数字、标点、编辑快捷操作和连续删除。按键标签、内部码元和编辑框显示内容分别管理。
4. 接入已验证的原生分组接口或独立拼音引擎，支持单字、词组、连续组句、分隔符和歧义候选；使用索引或音节图处理输入，避免对长串逐个枚举全部 `2^n` 字母组合。
5. 改造候选及编辑状态桥接，处理分页、部分选词、回车、组合态光标、选中替换、输入框切换、重启恢复及异步结果顺序；避免吞键、重字和旧候选提交。
6. 保存词频和用户词典，限定不同方案的存储；结构校验失败时保留原生布局和原生引擎，切换模式前正确处理未提交内容。

## “完整可用”的验收范围

这里列出开发验收要求，不表示本次已经通过。

| 范围 | 必须通过的行为 |
| --- | --- |
| 基础中文 | 全部 18 个键有效；单字、词组和连续句子可输入；相同分组序列的候选可区分；缺少现成词条时可逐字组成目标文本 |
| 候选和提交 | 点击、展开、分页、空格首选、分段选词和连续输入稳定；无候选输入可修改或明确提交，不丢失内容 |
| 纠正输入 | 退格一次删除一次分组输入；长按连续删除可靠；确定字母、拼音分隔及组字修正可用 |
| 英文和混输 | 26 个字母均可确定输入，支持大小写、数字和常用符号；网址、邮箱等文本能准确输入；密码框沿用正确的输入与学习策略 |
| 图片快捷操作 | 若宣称图片行为完整，数字和符号快捷输入、全选、复制、粘贴、段首/段尾及清空都有可发现的入口和明确作用范围 |
| 编辑框行为 | 微信/聊天、系统搜索、浏览器/WebView、笔记及多行编辑框；发送/搜索/下一项动作正确；选择替换和移动光标后继续输入一致 |
| 模式和生命周期 | 中英文、数字、符号、语音和工具面板往返；收起再打开、换应用、换输入框、横竖屏、进程重启后无残留候选和重复提交 |
| 持久化 | 用户选择和词频保存可靠，重启后仍可读；方案词典隔离；启用和关闭后都能正常输入 |
| 布局兼容 | 手机竖屏/横屏及声明支持的平板/折叠屏布局；字号、深浅色、外观和键盘高度改动后，触摸命中与显示位置一致 |
| 性能和回退 | 冷启动、长组合串、快速输入、连续删除和候选展开不卡住主线程；记录按键到候选显示延迟、内存及异常，宿主结构变化时能恢复原生输入 |

可在目标手机上把常用输入的候选刷新延迟目标暂定为 p95 不超过 50ms，并与原生键盘对照；这是待测的工程目标，不是现有性能数据。至少进行一轮跨应用连续使用和回归后，再标记为日常可用。
