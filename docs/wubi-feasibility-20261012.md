# 为超级小爱输入法添加五笔的可行性评估

评估日期：2026-10-12。宿主：`com.xiaomi.type 0.2.1053.06f65b7c`。沿用[前一轮样本、哈希及依赖证据](wubi-analysis-20261012.md)。本轮检查引擎接口、候选选择、上屏与模块接入条件，并做公开五笔码表的离线解析；没有实现或安装五笔模块，暂无真机验证。

## 判断

**通过现有 Xposed 模块加入基础五笔，技术可行性较高，值得做小规模验证。建议使用独立码表引擎，复用宿主 26 键键盘、候选栏和上屏流程。**

“能按编码输出候选词”与“作为日常主力稳定使用”工作量差别很大。前者具备明确的静态接入依据，后者仍需处理编辑状态、切换、生命周期及宿主版本变化。现阶段不能承诺成功率、性能或跨版本兼容。

## 三种引擎路线

| 路线 | 可行性判断 | 优势 | 主要未知或成本 |
| --- | --- | --- | --- |
| 激活讯飞现有 WUBI 模式 | 未证实，只适合限时验证 | 如果底层完整支持，可能复用更多行为 | 仅发现常量；无对应加载链路，词库格式、所需资源及运行结果未知 |
| 模块自带 Kotlin/Java 码表引擎 | 较高，优先推荐基础版本 | 可离线、无需新增 JNI；规则与词库可控 | 需实现候选排序、选词、顶屏及用户词频；复杂混输功能需额外开发 |
| 接入 librime | 较高，但集成复杂度更高 | 可复用成熟五笔方案和用户词典机制 | Android native 构建、JNI、库加载、数据部署及会话同步成本更高 |

Rime 提供[五笔 86 方案和码表](https://github.com/rime/rime-wubi)，并提供五笔拼音混输配置；[librime 的 C API](https://github.com/rime/librime/blob/master/src/rime_api.h)具有按键处理、候选上下文、选词和提交接口。它们解决的是引擎能力，不能自动完成小米宿主适配。

本项目目前使用 Kotlin/Java 与 DexKit，没有五笔实现或 librime 的 NDK/JNI 构建链路。对首版纯五笔而言，直接引入完整 librime 的工程成本未必合算。

## 可以复用的部分

以下路径均相对于 `work/xiaoai-21053/jadx/sources/`：

- `z8/q.java`：通用输入引擎接口，覆盖输入、状态、清空、选词和生命周期等。
- `z8/p.java`：扩展接口，包含 `h(char)`、`n(int,String)`、`m(int,int)` 等字母输入、候选选择和候选分页入口。
- `z8/r.java:31`：`InputResult` 已有 `consumed`、`composingText`、`candidates`、`commitText`、`deleteCount`、`acceptedRawInput`，能够承载五笔结果。
- `z8/a.java:21`：`Candidate` 有文字、注释、权重、来源及显示文字；不要求候选必须来自讯飞原生对象。
- `z8/s.java:18`：编码状态具有 rawInput、displayText、cursorPosition 等字段，可用于显示五笔编码。
- `ab/s0.java:117`：候选点击优先调用 `z8.p.n`；`ab/s0.java:153` 的分页调用 `z8.p.m`，主要依赖引擎接口。
- `ab/y1.java:233`：最终经宿主文本操作器调用 `InputConnection.setComposingText`；提交也经现有 `commitText` 路径。

这些说明独立引擎具有接入候选和文本管线的机会，并不代表替换一个方法即可完成全部交互。

## 建议的模块接入方式

1. 增加模块自己的五笔启用配置，原型先在模块设置中切换。
2. 宿主选择现有 `PINYIN` / 26 键类型时，在 `ab.x0.b(z8.g)` 或 `r9.h.a(z8.g)` 的创建入口按配置返回自有引擎。
3. 自有引擎适配宿主的 `z8.p`，把查表结果转换为宿主 `Candidate` / `InputResult` / composing 状态对象。
4. 保留已有 `PINYIN` 枚举作为内部类型标识，五笔状态由模块单独记录；随后再适配名称、入口与拼音专用交互。
5. 关闭五笔或结构检查失败时恢复原有创建路径；切换前显式处理编码和候选状态，避免半截编码进入下一引擎。

内部借用 `PINYIN` 有实际原因：`ab/f1.java:888` 的一条输入分支同时检查引擎类型为 PINYIN/T9、状态为 `z8.s`；`u9/d0.java` 也有类似 composing 判断。直接增加名为 WUBI 的枚举，会牵动布局和多处类型判断。

可首先尝试通过宿主 ClassLoader 创建实现其接口的 Java 动态代理，再反射构造结果对象；也可使用针对宿主接口编译的桥接实现。这是待验证的工程方案，类可见性、Kotlin Pair 返回值、默认方法、Object 方法和实例身份都需正确处理。不能在模块中定义同名接口，再假定宿主把它当成同一个类型。

初版仅在 26 键中文布局启用，不接管九键、英文、手写和笔画。此方案仍需检查 PINYIN 的纠错、防误触、数字混输及组合文本编辑逻辑；内部借用类型不等于这些语义天然兼容。

- 编码长度 1 至 4；有码词频字段，可用于初始候选排序。
- 精确查表确认：`wqiy → 你`、`vbg → 好`、`wqvb → 你好`。
- 文件 SHA-256：`f833d86b72341fe82e069a425b6625f29ef85f1bc0f34f6fb7975fe514888b5a`。
- 本地统计：`work/wubi-analysis-20261012/wubi-table-assessment.json`；本地码表同目录。

这证明有可直接解析的公开数据，无需先破解讯飞词库。建议构建时生成紧凑索引，运行时按编码查询，避免每次按键扫描全文。文件大小不能直接等同于运行时内存；本轮没有手机端延迟和内存数据。

引擎与码表许可证需要分别处理：[librime 使用 BSD 3-Clause](https://github.com/rime/librime/blob/master/LICENSE)，上述[五笔方案仓库标示 LGPL-3.0](https://github.com/rime/rime-wubi/blob/master/LICENSE)，不能把引擎许可直接套用到码表。

## 最小验证范围与验收

最先做一个固定版本、五笔 86、26 键的原型，覆盖：

- 字母编码和一至四码候选；编码、首屏候选同步刷新。
- 空格首选、点击候选、连续输入和退格；确认不会重复提交或吞掉下一组编码。
- 重码选择，以及四码唯一候选自动上屏、第五码顶屏的明确配置和行为。
- 中英文切换、数字和标点插入、收起再打开、切换输入框时正确清理或提交状态。
- 候选展开/分页、全选替换、移动光标后继续输入；不能只验证一个编辑框。

用户词频、自造词、拼音反查、混输、86/98/新世纪多码表、字根键帽和原生设置页入口可以分阶段增加。工具栏和 AI 面板预计可继续沿用宿主，但五笔输入与语音/翻译切换时的兼容性仍需实测。

## 工作量估算

下面是熟悉本项目和 Android/Xposed 的一名开发者、拥有在线测试机、限定 0.2.1053 的粗估，不是交付承诺：

| 阶段 | 估算 | 产出 |
| --- | --- | --- |
| 验证宿主引擎替换与一组真实编码输入 | 1–3 个工作日 | 真机证明键盘 → 自有引擎 → 原生候选 → 上屏链路可用 |
| 基础五笔 86 原型 | 累计约 3–7 个工作日 | 常用编码、选词、退格、基本切换；需继续排查边界问题 |
| 单版本日常使用版本 | 累计约 2–4 周 | 状态回归、用户配置、词库加载优化及常见应用验证 |

多版本自适配和复杂混输需另行估算。现有 DexKit 定位机制可复用，但需要新增五笔相关特征；发现名字变化并不代表接口语义没有变化。

修改并重签官方 APK 也可承载同样的独立引擎，但会带来系统组件升级、签名和每次更新重新合并改动的成本。基于本项目已有模块基础，优先选择模块接入。

## 当前证据的限制

`adb devices -l` 没有在线设备。本轮完成的是静态接入评估和桌面码表解析，没有证明动态代理能在该宿主正常运行，也没有确认五笔和所有既有功能兼容。

建议下一项实际开发先集中验证引擎替换、原生候选点击和上屏三件事。若该链路成立，再扩展词库和交互；若因宿主具体类型依赖失败，先调整为包装/拦截现有引擎，再考虑更大范围改包。讯飞原生 WUBI 模式可另做限时探测，但不宜作为整个实现的前提。
